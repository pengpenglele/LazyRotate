## 0. 结论（只看这一节）

### 0.1 一句话结论

**工程可以交给用户在 DevEco Studio（API 26 / 鸿蒙 7）里打开、Sync、构建，但交付前必须先修 2 个功能性硬伤（FAIL），并在 IDE 里确认 1 个 P0 版本配置风险（WARN）。**

本报告**没有**、也**不能**写「已验证可编译」——见 0.2。

| 项 | 数量 | 说明 |
|---|---|---|
| FAIL（必须修） | **2** | 均为「目标设备上的核心功能错误」，不是编译错误；修法都在 1~2 个函数内 |
| WARN | **18** | 含 1 个 P0「打开/Sync 风险」（版本字段匹配，无法在本机证明） |
| 自检脚本 | **18 通过 / 0 警告 / 0 失败** | 复跑结果，见第 2 节 |
| 编译 / 运行 / 真机 | **0 项** | 本机无 DevEco Studio、无 HarmonyOS SDK，未编译、未运行 |

### 0.2 为什么不能给「已验证可编译」的结论（客观原因）

1. 本机**没有安装 DevEco Studio，也没有 HarmonyOS SDK / full SDK**，无法执行 `hvigor` / ArkTS 编译器，无法产出 HAP；
2. `tools/verify-harmony.py` 是**自检脚本**，只做 JSON5 解析、资源引用、import 路径、括号配对、权限/依赖/系统接口卫生检查，**不解析 ArkTS 类型、不校验 SDK 签名**；
3. 因此本报告能证明的只有：「配置/资源/代码结构在静态层面自洽，所调用的公开 API 在官方文档中存在且签名匹配」。**不能证明**：能编译、能安装、方向接口在目标平板上实际生效。
4. 若 DevEco 打开时报错，**以 IDE 报错为准**；本报告第 5.1 节给出了最可能的报错来源与兜底方案。

### 0.3 两条 FAIL（先修这两条，再交付）

| # | 硬伤 | 位置 | 影响 |
|---|---|---|---|
| FAIL-1 | 「跟随系统」映射到 `AUTO_ROTATION`，该枚举**不受控制中心旋转锁定开关控制** | `SelfWindowBackend.ets:59` | 用户按 App 引导打开系统旋转锁定后，点「跟随系统」反而让本应用窗口**摆脱**系统锁定——与产品文案/卖点相反 |
| FAIL-2 | 用 `display.rotation` 直接映射方向目标，**忽略屏幕自然方向** | `Contract.ets:104-130`、`RotationService.ets:52-62`、`Index.ets:894-909` | 在「自然方向为横屏」的平板（本工程的目标设备）上，「锁定当前」「翻转 180°」会**转到错误方向** |

两条都是**函数级小改**，但都会直接毁掉核心体验，**不建议带病交付**。

### 0.4 一个 P0 配置风险（无法在本机证明，需 IDE 确认）

`oh-package.json5` 的 `modelVersion = 6.0.0`、`hvigor/hvigor-config.json5` 的 `hvigorVersion = 6.0.0` / `@ohos/hvigor-ohos-plugin = 6.0.0`，与 `build-profile.json5` 的 `compatibleSdkVersion = 7.0.0(26)` 是否属于同一代工具链，**本机无法验证**；社区资料对 API 26 的版本字段格式与 IDE 版本号存在两种说法（`7.0.0(26)` vs `26.0.0`；DevEco 6.0 / 7.0 / 26.0.0）。若未对齐，**第一次打开/ Sync 就会失败**。构建说明第 5 节已经写了兜底（Migrate / 改 `modelVersion`+`hvigorVersion` / 新建 API 26 工程覆盖源码），**按那里做即可，不需要改业务代码**。

- **PASS**：文档原文可证明用法/字段/签名成立，且静态阅读未发现冲突；

## 4. FAIL 详情（必须修）

### FAIL-1 「跟随系统」用了不受系统旋转锁控制的枚举

**位置**：`harmony/LazyRotate/entry/src/main/ets/core/SelfWindowBackend.ets:59`

```ts
default:
  return window.Orientation.AUTO_ROTATION;   // ← 这里
```

**文档证据**（[arkts-apis-window-e.md#orientation9](https://gitee.com/openharmony/docs/blob/master/zh-cn/application-dev/reference/apis-arkui/arkts-apis-window-e.md)）：

| 枚举 | 文档原文（节选） |
|---|---|
| `AUTO_ROTATION` | 跟随传感器自动旋转，可以旋转到四个方向，**且不受控制中心的旋转开关控制** |
| `AUTO_ROTATION_RESTRICTED` | 跟随传感器自动旋转，可以旋转到四个方向，**且受控制中心的旋转开关控制** |
| `AUTO_ROTATION_UNSPECIFIED` | 跟随传感器自动旋转，**受控制中心的旋转开关控制**，且可旋转方向受系统判定 |

**冲突证据（工程内文案）**：

- `Contract.ets:88`：`'交还系统，跟随重力与系统旋转锁定开关'`
- `Index.ets:519-528`「控制中心旋转锁定（系统级，推荐日常使用）」：教用户打开控制中心旋转锁定，然后期望本应用跟随系统锁
- `Index.ets:523`：`"3. 躺姿下锁定后，系统不再根据重力猜方向"`

**影响**：用户点「跟随系统」后，本应用窗口会切到 `AUTO_ROTATION`，**忽略**用户在控制中心打开的旋转锁定——恰好与 App 的说明页相反。这是产品叙事级错误，优先级最高。

**修复建议**（二选一，推荐 A）：

```ts
// A. 「跟随系统」= 真正受系统旋转锁控制
default:
  return window.Orientation.AUTO_ROTATION_RESTRICTED;

// B. 更接近「交还系统默认策略」语义
default:
  return window.Orientation.AUTO_ROTATION_UNSPECIFIED;
```

同时把 `Contract.ets:88` 的 hint 文案与修复后的语义对齐（若选 A 可直接保留原文案；若选 B 建议改为「交还系统，由系统判定方向」）。

### FAIL-2 「锁定当前 / 翻转 180°」用 `display.rotation` 直映射，平板上方向会反

**位置**：

- `Contract.ets:100-115` `fixedTargetForRotation(rotation)`
- `Contract.ets:117-131` `flippedTargetForRotation(rotation)`
- `RotationService.ets:52-62`（`lockCurrent` / `flip` 先 `readDisplayInfo()` 再映射）
- `Index.ets:894-909`（悬浮球循环也用同一映射）

**文档证据**（[js-apis-display.md](https://gitee.com/openharmony/docs/blob/master/zh-cn/application-dev/reference/apis-arkui/js-apis-display.md)）：

- `Display.rotation`：「显示设备的屏幕顺时针旋转角度。**值为 0 时……表示显示设备的（标准/自然）显示方向**；1=90°，2=180°，3=270°」
- 同模块另有 `Display.orientation: display.Orientation`，枚举直接给出 `PORTRAIT / LANDSCAPE / PORTRAIT_INVERTED / LANDSCAPE_INVERTED`（与 `window.Orientation` 一一对应语义）

**问题**：`rotation` 是**相对自然方向**的角度，不是相对竖屏。本工程的目标设备是**平板**（`module.json5` deviceTypes 含 tablet/2in1；构建说明要求「一台鸿蒙 7 平板/手机」，且设计围绕躺姿平板）。平板自然方向通常是**横屏**，于是：

| 实际状态 | `display.rotation` | 代码锁定为 | 期望 |
|---|---|---|---|
| 平板自然横屏（横放） | 0 | `PORTRAIT` ❌ | `LANDSCAPE` |
| 旋转 90°（竖放） | 1 | `LANDSCAPE` ❌ | `PORTRAIT` |
| 旋转 180° | 2 | `PORTRAIT_INVERTED` ❌ | `LANDSCAPE_INVERTED` |

「翻转 180°」同理：平板上从横屏翻转，代码会翻成 `PORTRAIT_INVERTED`，画面直接变成竖屏，而不是横向翻转。

> 注：手机（自然竖屏）上现有映射恰好正确，所以该 bug 在手机上不易暴露——这正是它危险的地方。

**修复建议（推荐）**：方向目标改由 `display.orientation` 派生（枚举语义与 `window.Orientation` 对齐），翻转改为「对当前目标取反」：

```ts
// Contract.ets
export function fixedTargetForOrientation(o: display.Orientation): RotationTarget {
  switch (o) {
    case display.Orientation.LANDSCAPE:          return RotationTarget.LANDSCAPE;
    case display.Orientation.PORTRAIT_INVERTED:  return RotationTarget.PORTRAIT_INVERTED;
    case display.Orientation.LANDSCAPE_INVERTED: return RotationTarget.LANDSCAPE_INVERTED;
    default:                                     return RotationTarget.PORTRAIT;
  }
}

export function flippedTarget(t: RotationTarget): RotationTarget {
  switch (t) {
    case RotationTarget.PORTRAIT:            return RotationTarget.PORTRAIT_INVERTED;
    case RotationTarget.PORTRAIT_INVERTED:   return RotationTarget.PORTRAIT;
    case RotationTarget.LANDSCAPE:           return RotationTarget.LANDSCAPE_INVERTED;
    case RotationTarget.LANDSCAPE_INVERTED:  return RotationTarget.LANDSCAPE;
    default:                                 return RotationTarget.PORTRAIT_INVERTED; // AUTO 时按当前 orientation 先落一个方向
  }
}
```

- `lockCurrent` → `fixedTargetForOrientation(readDisplayInfo().orientation)`
- `flip` → `flippedTarget(currentFixedTarget)`（若当前是 AUTO，先用 orientation 落一个固定方向再翻转）
- 同步把 `DeviceState.ets:46-57` 的 `rotationLabel`（0°/90°…）改成展示 `orientation`，避免 UI 出现「横屏 · 0°」的困惑。

**为何不直接改为 `window.LOCKED`**：`Orientation.LOCKED` 表示「窗口显示方向与屏幕当前方向一致」，看起来更贴合「锁定当前」，但它锁的是「当前屏幕方向」，在 AUTO 状态下与旋转锁/系统判定交互更复杂，且文档说明仍受窗口状态限制。若想最小改动且语义最直观，可评估 `LOCKED`，但**必须真机验证**（已列入第 6 节）。

### 5.2 会导致运行异常 / 功能不符预期的风险

#### WARN-3 应用在前台时，外部指令不会立即生效（onNewWant 只写不消费）

- **位置**：`EntryAbility.ets:21-23、35-42`；`Index.ets:116-122、829-844`
- **现状**：`onNewWant` 把指令写进 `AppStorage.pendingCommand`；只有页面 `onPageShow` 才消费。应用已在前台（页面已显示）时重复 `hdc aa start`，**不会触发 onPageShow**，`@StorageLink` 也没有 `@Watch`，指令会一直挂着，直到用户切后台再回来（或页面重建）。
- **修复**：给 `@StorageLink('pendingCommand')` 加 `@Watch('onPendingCommandChange')` 并在回调里消费；或在 `EntryAbility.onForeground()` 里把指令转成 emitter 事件/`AppStorage` 之外的队列，由页面统一消费。注意官方**不建议**用 `@StorageLink` 做事件通道（可用 AppStorage API + `@Watch`，或 `emitter`）。

#### WARN-4 启动恢复与 pendingCommand 存在竞态

- **位置**：`Index.ets:104`（`restoreLastTarget()`）、`Index.ets:121`（`consumePendingCommand()`）、`RotationService.ets:70-79`
- **现状**：`aboutToAppear` 里启动恢复是 async（等 `getLastWindow` + `setPreferredOrientation`）；`onPageShow` 里消费指令也是 async。两个 `setPreferredOrientation` 并发，完成顺序不确定，**最终方向可能是“恢复值”覆盖“外部指令”**。
- **修复**：在 `aboutToAppear` 里先判断 `AppStorage.get('pendingCommand')` 非空则跳过恢复；或把「恢复/指令」串成一个队列（同一时刻只允许一个写方向操作）。

#### WARN-5 未知/缺参的外部指令会切到「跟随系统」，与「不确定就不动」矛盾

- **位置**：`Contract.ets:65-67`（default → AUTO）、`Contract.ets:61-64`；`RotationCommand.ets:53-55`（`SET_ROTATION` 无 target → TARGET AUTO）；`Index.ets:843`
- **现状**：未知 target 被解析成 `AUTO` 并真的执行 `followSystem`，即**改状态**。
- **冲突**：`docs/鸿蒙版-可行性评估.md:338-339` 明确要求「未知 `target` → 忽略并保持现状，不崩溃」。
- **修复**：`parseRotationTarget` 增加「未知」信号（如 `RotationTarget` 之外返回 `null`/`undefined` 或抛受控错误），`parseRotationCommand` 对未知/缺参返回 `null`，`consumePendingCommand` 收到空/未知时只提示不执行。

#### WARN-6 `setPreferredOrientation` 静默不生效，但 UI 会报「已应用」

- **位置**：`SelfWindowBackend.ets:27-45`（成功即 `ok: true`）；`Index.ets:851-856` 等
- **证据**：窗口文档明确：「设备支持 sensor 旋转且**未处于自由窗口**状态：立即生效；处于自由窗口：调用不生效不报错；其他情况：不生效不报错」。
- **影响**：平板/2in1 处于自由多窗/分屏/悬浮时，点按钮提示「已应用（仅本应用窗口）」，但画面没变 → 用户认为坏了。
- **修复**：
  1. 调用后回读 `window.getPreferredOrientation()` 或 `display.getDefaultDisplaySync().orientation` 做**回读校验**（与可行性评估 4.3「回读校验」一致）；
  2. 可用 `window.getWindowStatus()` 判断 `FLOATING/SPLIT_SCREEN` 并提示「当前窗口模式下方向设置不生效，请切换全屏/非自由窗口」。

#### WARN-7 `display.on('change')` 回调参数是屏幕 ID，不是 rotation

- **位置**：`DeviceState.ets:60-66`
- **证据**：[js-apis-display.md](https://gitee.com/openharmony/docs/blob/master/zh-cn/application-dev/reference/apis-arkui/js-apis-display.md) `display.on('add'|'remove'|'change', callback: Callback<number>)`：「回调函数。**返回监听到的屏幕 ID**」。
- **现状**：`subscribeDisplayChange(onChange: (rotation: number) => void)` 把 `data` 当 rotation 命名传递，但 `Index.ets:99-102` 忽略该值、重新 `readDisplayInfo()`，**当前不炸**。
- **风险**：签名/命名误导，后续若有人直接使用这个参数就会写错逻辑。
- **修复**：重命名为 `onChange: (displayId: number) => void`，或干脆声明为 `() => void`，避免误用。

#### WARN-8 用 `@StorageLink` 做事件通知

- **位置**：`Index.ets:54`、`EntryAbility.ets:40`、`Index.ets:834`
- **证据**：[arkts-appstorage.md「不建议借助 @StorageLink 的双向同步机制实现事件通知」](https://gitee.com/openharmony/docs/blob/master/zh-cn/application-dev/ui/state-management/arkts-appstorage.md)
- **建议**：保留 AppStorage 作为状态没问题，但事件通知建议改 `emitter`，或至少加 `@Watch` 并确保不把 `pendingCommand` 绑定到 UI（当前它没有渲染，问题不大，属结构优化）。

#### WARN-9 `openDisplaySettingsPage` 在「不生效」设备上会误报成功

- **位置**：`SystemRotationSettings.ets:39-49`（`deviceInfo.sdkApiVersion >= 26` 即 `return true`）
- **证据**：settings 文档「设备行为差异：该接口在 Phone、Tablet、PC/2in1 设备中可正常调用，在其他设备**调用不生效**」（无异常）。
- **影响**：在 tv/车机等设备（虽然 module.json5 未声明，但用户可能改）点按钮，UI 提示「已打开」，实际没跳。
- **建议**：结合 `deviceInfo.deviceType` 判断，或把提示改成「已请求打开，若未跳转请手动：设置 > 显示和亮度」；catch 里区分 `16900010/16900020`。

#### WARN-10 偏好初始化失败会静默失去全部持久化

- **位置**：`AppPreferences.ets:16-22`（`getPreferencesSync` 失败 → `store = undefined`）、所有 `put/get` 变空操作
- **影响**：`restoreOnLaunch` 永远读默认 `true`、`lastTarget` 永远 AUTO、悬浮球位置不保存，但 UI 无任何提示；用户会认为「启动恢复/记住位置」坏了。
- **建议**：暴露 `isAvailable()` 给 UI，失败时在设置页提示「本机偏好存储不可用，本次不保存设置」。

#### WARN-11 躺姿阈值与置信度是假设值，未做迟滞

- **位置**：`LieDownEngine.ets:74-89`（`|z|>7 && inPlane<4`）、`LieDownEngine.ets:40-52`（`lying` 变化或 400ms 节流）
- **影响**：平板平放/手持姿态切换时可能抖动，置信度语义（`(4-inPlane)/4`）与 Android 版「置信度 0.25 + 迟滞 700ms」不可直接对标；UI 文案「屏幕接近水平…建议锁定」可能频繁闪。
- **建议**：真机采数后再定阈值；加双阈值迟滞（进入/退出不同门限）；把 `tiltDeg`/`confidence` 一起参与判定。

#### WARN-12 读取系统「自动旋转」状态在三方应用里可能拿不到

- **位置**：`SystemRotationSettings.ets:15-26`
- **现状**：文档未声明 `getValueSync` 读权限，但系统数据项对三方可见性受系统策略影响；代码已兜底 `'unknown'`，UI 显示「未知（系统可能未开放读取）」。
- **结论**：**不是 bug，是已知限制**；真机确认后把文案定稿即可（第 6 节第 7 项）。

#### WARN-13 悬浮球位置按「屏幕尺寸」而非「窗口可用区域」夹取

- **位置**：`Index.ets:755-787`（`display.width/height` → `px2vp` → clamp）、`position({x,y})`
- **影响**：自由窗口/分屏/2in1 下窗口小于屏幕时，球可能被限制到窗口外或压住底部栏；`screenH-140` 是写死的经验值。
- **建议**：用 `window.getLastWindow(this.context).getWindowProperties().windowRect` 或 `onAreaChange` 获取实际窗口尺寸做 clamp；底部安全区改用 `avoidArea`/`getWindowAvoidArea`。

#### WARN-14 自定义 skills（只有 actions）的隐式匹配语义未经真机验证

- **位置**：`module.json5:35-41`
- **现状**：schema 合法（actions/entities/uris 均可缺省，actions 允许自定义）；`exported: true` 保证显式拉起；三个自定义 action 与代码/文档一致。
- **风险**：若用户尝试用**隐式**方式（只给 `-A` 不给 `-a/-b`）拉起，是否命中取决于实体匹配规则与 skill 组合；且 aa 文档把 `-A` 放在「隐式启动」语法组。
- **建议**：文档明确只支持**显式**拉起（`-b ... -a EntryAbility -A ...`）；若要支持隐式，给 skill 补 `entities`/`uris` 并在真机上验证匹配。

#### WARN-15 aa 显式启动携带 `-A`/`--ps` 的送达行为待真机确认

- **位置**：`docs/鸿蒙工程-构建与运行.md:63-72`、`README.md:14`、`Index.ets:47-48`
- **现状**：命令写法与 aa 工具参数表一致（`--ps` 存在，字符串不能以 `-` 开头），但 aa 文档把 `-A` 归在隐式启动语法组；**显式启动 + action 是否能原样进 `Want.action`** 需要真机抓一次（见第 6 节第 11 项）。
