# 屏幕方向控制 LazyRotate · 鸿蒙版可行性评估

> 评估对象：安卓平板「屏幕方向控制 LazyRotate」移植到 **鸿蒙 7（API 26）**，以及其核心卖点「真·全局屏幕方向锁定」在鸿蒙上是否成立。
> 评估方式：只采信 OpenHarmony / Huawei 官方文档与系统接口清单（证据见文末《证据链接清单》），
> 其中 `@ohos.screen`（系统接口）、`@ohos.settings`、`@ohos.enterprise.deviceSettings` 三份原文已在 2026-10-19 逐条核对。
> 凡本次没有拿到文档证据的能力，一律标注 **「待真机验证」**，不做承诺。
>
> 本文只描述能力边界与建议架构，不含代码改动。

---

## 0. 结论先行（只看这一节也能决策）

**一句话结论：普通第三方应用无法全局锁定或翻转其它 App 的方向。** 这是鸿蒙的架构级隔离，
不是权限数量或声明写法问题。真·全局方向锁定只有一条路——**系统签名 / 预置应用**，
而且它拿不到普通 AGC 应用市场的发布通道。

| 问题 | 结论 | 依据 |
|---|---|---|
| 三方应用能否全局锁定方向（其它 App 一起锁） | **不能** | 应用侧只有本应用窗口的方向接口（`window.setPreferredOrientation` 等），作用域就是自己的窗口 |
| 三方应用能否全局翻转 180° | **不能** | 其它 App 一律无法翻转；本应用窗口内的「反向方向」还受设备与应用旋转策略约束，是否被接受**待真机验证** |
| 应用退出后，系统是否仍保持锁定 | **不能由本应用保证** | 每个应用各按自己的旋转策略执行；系统级旋转开关在「设置 / 控制中心」，属于系统 UI |
| 有没有系统级接口可以做到 | **有，但是系统接口** | `screen.setScreenRotationLocked` / `screen.isScreenRotationLocked` / `Screen.setOrientation` / `window.setRotationLocked` 均为系统接口，非系统应用调用返回 **202** |
| MDM / 企业设备管理能否变通 | **不能** | API 26 的 MDM Kit（`deviceSettings` / `restrictions` / `applicationManager`）没有旋转/方向策略 |
| 无障碍注入能否变通 | **不能** | `AccessibilityExtensionAbility` 的 `onAccessibilityEvent` / `onKeyEvent` / `onConnect` 自 **API 12 起废弃**，系统不再开放，且它本身也不具备设置旋转的能力 |
| 那还能做什么 | **做「应用内方向控制 + 系统设置引导 + 可插拔特权后端」** | 见第 5 节；这是三方身份下唯一能落地且不撒谎的产品形态 |

**代价与取舍（务必写进产品文案）**：

1. 免特权档位只能保证「本应用自己的窗口」方向正确，切到别的 App 就交还控制权；
2. 想影响全局，只能**引导用户手动**去「设置 → 显示和亮度」或控制中心打开旋转锁定（API 26 提供了 `settings.openDisplaySettingsPage(context)` 直接跳转，Phone/Tablet/PC 可用）；
3. 要真正自动全局，必须走系统签名/预置路线：需要系统应用权限 + **full SDK**（系统接口不在 public SDK 里）+ 系统签名/profile，且**不能通过普通 AGC 发布**；
4. 电脑侧 `hdc` / `uitest uiInput` 自动化点控制中心可以做演示，但它需要一台电脑、依赖 UI 坐标、系统改版就失效，只能当兜底，不能当产品。

> ⚠️ **不允许出现的表述**：「鸿蒙上可以直接全局锁定方向」「装了本应用就能锁住所有 App 的屏幕」。
> 这两句话在本评估中已被证伪，任何对外文档、商店描述、UI 文案都不得使用。

## 1. 版本与工程基线

| 项目 | 取值 | 说明 |
|---|---|---|
| 系统版本 | 鸿蒙 7 | 代号/大版本 |
| API 版本 | **API 26** | 与鸿蒙 7 对应 |
| 版本字符串 | `7.0.0(26)` | 设置里的展示形态 |
| 目标 SDK | **26** | 新接口（如 `settings.openDisplaySettingsPage`、MDM `setSwitchStatus`）均以「起始版本 26.0.0」标记 |

**三个 SDK 版本字段的关系**（工程 `build-profile.json5` 里的配置项）：

| 字段 | 语义 | 本项目建议 |
|---|---|---|
| `compatibleSdkVersion` | 最低兼容版本：设备 API ≥ 它才能安装运行；取低值可扩大覆盖，但用不到新接口 | 本工程**有意取 26**：因为用了 API 26 的 `settings.openDisplaySettingsPage`，且目标设备就是鸿蒙 7 平板；若要覆盖鸿蒙 6（API 20），需降到 `6.0.0(20)` 并对该 API 做版本判断 |
| `targetSdkVersion` | 目标版本：决定系统以哪一版行为对待本应用（行为门） | 26（与鸿蒙 7 对齐） |
| `compileSdkVersion` | 编译所用 SDK 版本：决定能引用到哪些接口与 d.ts | 26；**系统接口需要 full SDK 才编得过**（见第 4 节） |

> ⚠️ 「兼容版本取 26 就万事大吉」是常见误解：`compatibleSdkVersion` 只决定装得上装不上，
> 真正决定「系统按哪版行为对待你」的是 `targetSdkVersion`，
> 决定「能写出哪些 API 调用」的是 `compileSdkVersion`（以及它是 public 还是 full SDK）。
> 本项目的接口面非常窄（窗口方向 + 设置页跳转 + Want），没有必须追新的理由，**稳重取 26 即可**。

## 2. 安卓版能力 vs 鸿蒙能力对照矩阵

图例：**可** = 三方应用在 public SDK 下能做；**受限** = 能做但作用域/条件受限；**不可** = 三方身份下做不到；
**待真机验证** = 缺少文档证据，需在真机上确认后再写进对外文案。

| 能力项 | 安卓版（现状） | 鸿蒙（API 26，三方） | 依据 / 备注 |
|---|---|---|---|
| **全局锁定方向** | 可（`WRITE_SETTINGS` 写 `accelerometer_rotation` + `user_rotation`；硬锁方向的应用除外） | **不可** | 三方只有 `window.setPreferredOrientation`，作用域是本应用主窗口；全局接口全在系统接口清单里 |
| **180° 翻转** | 可（写 `user_rotation=2`；部分机型/应用受限） | **受限 → 待真机验证** | 本应用窗口内指定反向方向是否在平板上生效需实测；其它 App 无法翻转 |
| **跟随系统（交还控制权）** | 可 | **可** | 本应用窗口可声明跟随传感器/系统；退出本应用后由系统与前台应用决定 |
| **快速设置磁贴** | 可（`TileService`，API 24+） | **受限 → 待真机验证** | 本次未核实到与 Android `TileService` 对等的三方快速设置磁贴 API；入口需另找（服务卡片/桌面快捷方式等），**不得按 Android 的用法直接承诺** |
| **悬浮球** | 可（`SYSTEM_ALERT_WINDOW`） | **受限 → 待真机验证** | 鸿蒙侧是否存在免特权的常驻悬浮窗（及所需权限）本次无证据；且即便有悬浮窗，也**不能**靠它给别的 App 定方向 |
| **常驻通知** | 可（前台服务 + 通知） | **可（受限）** | 基础通知能力三方可用；受通知授权与后台/常驻限制约束，长时间驻留策略**待真机验证** |
| **按应用规则** | 可（无障碍读前台包名 + 切方向） | **不可** | 需要「感知其它应用」的能力；鸿蒙无障碍注入路线自 API 12 起不再开放（见路线 D），且本应用无其它合法途径获取前台应用并改其方向 |
| **躺姿引擎** | 可（传感器 + 置信度迟滞，全局生效） | **受限** | 传感器数据可用于计算建议方向，但结果**只能作用于本应用窗口**；无法把建议施加到其它 App |
| **外部指令** | 可（`am start` / `am broadcast`） | **可（受限）** | 鸿蒙用 Want（显式/隐式 action + parameters）拉起本应用 UIAbility；仍只影响本应用窗口 |

**矩阵读法**：安卓版之所以「看起来很全局」，是因为 `WRITE_SETTINGS` 能改系统级旋转设置且对大屏应用有效；
鸿蒙侧**不存在等价的免特权系统级写入口**——`settings.setValue` 需要 `ohos.permission.MANAGE_SETTINGS`，
而该权限**仅系统应用可用**。这就是两条平台能力差距的根，不是实现技巧问题。

## 3. 路线逐条评估（A–E 为五条主路线，F 为额外说明）

### 路线 A：普通第三方应用（`window.setPreferredOrientation`）

**能做什么**：设置**本应用主窗口**的首选方向（竖屏/横屏及其组合、跟随传感器等）。
全屏前台运行时，屏幕会跟随本应用的声明旋转，用户能获得「进入本应用即按我定的方向显示」的体验。

**不能做什么**：影响不了别的应用。退出本应用（或它的窗口不在前台）后，
系统与前台应用各按自己的旋转策略走，本应用无从干预。

**工程含义**：

- 这是 harmony/ 默认构建（public SDK）里**唯一**能真正生效的方向手段；
- 必须处理「声明方向与设备能力不匹配」的降级分支——具体哪些方向枚举在平板/折叠屏上生效，**待真机验证**；
- UI 上必须明确区分「本应用方向」与「系统方向」，避免用户误以为已经全局锁定。

**结论**：**唯一无门槛路线，但天花板就是「我的窗口我做主」**。产品必须以此为主路径，并把能力边界讲清楚。

### 路线 B：系统签名 / 预置应用（系统接口）

**核心接口清单（均为系统接口）**：

| 接口 | 作用 | 非系统应用调用结果 |
|---|---|---|
| `screen.setScreenRotationLocked(isLocked: boolean)` | 设置屏幕旋转锁定（锁/解锁） | **202** |
| `screen.isScreenRotationLocked()` | 查询屏幕旋转是否锁定 | **202** |
| `Screen.setOrientation(orientation: Orientation)` | 设置屏幕方向（`Orientation` 枚举） | **202** |
| `window.setRotationLocked(...)` | 窗口/屏幕旋转锁定的系统接口 | **202** |

**错误码 202 原文**（来自 `@ohos.screen` 系统接口文档）：
`Permission verification failed. A non-system application calls a system API.`
—— 即「非系统应用调用系统接口」，属于**权限校验失败**，不是参数错误，**无法通过重试/换参绕过**。

**一个容易被忽略的细节**：`Screen.setOrientation()` 的文档明确写着，
只有当设置的方向**符合应用旋转策略**（`module.json5` 中 abilities 的 `orientation` 字段）时屏幕方向才会改变；
不符合时**方向不变，且接口不抛异常**。也就是说：即便拿到系统签名，方向设置也要和应用自身声明配合，
「静默不生效」是这条路上的真实风险，必须做**回读校验**（`screen.isScreenRotationLocked()`、读取实际方向）而不能只看调用成功。

**代价**：系统签名 + full SDK + 预置/系统应用身份，且**普通 AGC 发布拿不到**。详见第 4 节。

**结论**：**唯一能实现「真·全局锁定 + 全局翻转」的路线**，但只适用于自用、定制设备、行业预置等场景，
不能作为面向大众市场的产品形态。

### 路线 C：MDM / 企业设备管理

**核实结果：API 26 的 MDM Kit 没有旋转/方向策略。**

- `@ohos.enterprise.deviceSettings` 的 `setValue` 策略项为：
  `screenOff`（息屏时间）、`dateTime`（系统时间）、`powerPolicy`（电源策略）、
  `eyeComfort`（护眼模式，API 23+）、`defaultInputMethod`（默认输入法，API 23+）；
  API 26 新增的是 `setSwitchStatus`，且开关枚举只有**星闪 / 蓝牙 / Wi-Fi**。
  **全表没有任何 rotation / orientation 项。**
- `@ohos.enterprise.restrictions`：用于禁用能力/设备策略，同样**没有旋转策略**。
- `@ohos.enterprise.applicationManager`：应用管理（安装、Kiosk 等），**没有旋转策略**。
- 并且该 Kit 的使用门槛不低：**仅对设备管理应用开放，调用前需激活设备管理应用**；
  文档中给出的错误码 `9200001`（不是设备管理员应用）/ `9200002`（无权限管理设备）说明还需要
  企业证书与管理员权限（`ohos.permission.ENTERPRISE_MANAGE_SETTINGS` 等）。

**结论**：MDM 路线**不可行**——既没有对应策略，门槛也与普通三方应用无关。
（若客户愿意走企业定制 + 系统签名，直接把路线 B 的接口封进定制固件更直接。）

### 路线 D：无障碍注入

**核实结果：此路在鸿蒙上已关闭。**

`AccessibilityExtensionAbility` 的 `onAccessibilityEvent` / `onKeyEvent` / `onConnect`
**自 API 12 起废弃**，系统不再开放该能力。也就是说：

1. 本应用无法再像 Android 版那样通过无障碍事件读取前台应用包名 → **「按应用规则」在鸿蒙上失去感知基础**；
2. 无障碍本身**也不具备设置屏幕旋转的能力**——它没有旋转接口，即便事件可用也无从下手。

**结论**：**不可行，且不应在文档或文案中留下任何「未来开启无障碍就能全局控制」的暗示**。

### 路线 E：电脑侧 `hdc` / `uitest uiInput` 自动化控制中心

**可行性**：技术上是通的——用 `hdc` 连接设备，`uitest uiInput` 注入点击，展开控制中心、点旋转锁定。
可以用来做**演示、验收或一次性批量配置**。

**为什么只能当兜底**：

- **必须有电脑**：不是用户随手可用的产品形态；
- **脆弱**：依赖控制中心的位置、层级、动画时序；系统 UI 一改版就失效；
- **不可编程化**：脚本无法感知系统真实状态，只能「盲点」，误触风险高；
- **上架无意义**：应用商店不会接受「请把平板连到电脑」的核心功能。

**结论**：**仅作兜底手段**——写进高级用户文档、供需要的人复制命令，不进入产品主流程，不做自动重试。

### 路线 F：root / 刷机（额外说明，**不建议**）

- 与鸿蒙的设备安全模型正面冲突：解锁、刷机、root 会触发完整性校验，且**损害系统安全边界**；
- 对普通用户不可复制，售后成本极高；
- 一旦被用于「绕过系统权限」，会把应用推向**合规风险**（见第 6 节），商店与厂商政策的容忍度为零。

**结论**：**明确不建议**，本项目不实现、不引导、不提供脚本。

## 4. 系统签名路线（路线 B）的落地条件

如果目标场景是**自用设备 / 行业定制 / 预置出厂**，路线 B 是唯一能达成产品的方案。落地条件如下。

### 4.1 硬前置条件

| 条件 | 说明 |
|---|---|
| 系统应用权限 | 使用系统接口需要系统应用身份；`settings.setValue` 所需的 `ohos.permission.MANAGE_SETTINGS` 在权限清单中标注 **`system_basic` 级 + `ACL true`**，即需要 ACL 且仅系统应用可申请 |
| 其它相关系统权限 | 权限清单中还有 `PUBLISH_DISPLAY_ROTATION_EVENT` 等显示/旋转相关系统权限；具体需要哪几个**以 full SDK 中权限定义与接口文档为准，待真机验证** |
| **full SDK** | **系统接口不在 public SDK 中**：普通工程即便写对了 API 名也**编译不过**（找不到声明）或运行时报 202。必须使用 full SDK 编译 |
| 签名 / profile | 需要系统签名（profile 绑定系统应用身份），不是普通调试签名能覆盖的能力 |
| 分发限制 | **普通 AGC 发布拿不到**系统签名与系统应用身份；只能随定制固件/预置渠道交付 |

### 4.2 ArkTS 代码示例（警告：系统接口）

> ⚠️ **以下示例均为系统接口，需系统签名 + full SDK。**
> **放在普通（public SDK）工程里编译不过**，运行亦会返回 202。
> 本仓库 `harmony/` 默认构建**不包含**这些调用，仅作为特权后端的参考片段保留。

```ts
// ⚠️ 系统接口示例（需系统签名 + full SDK，普通工程编译不过）
import { screen, window } from '@kit.ArkUI';
import { BusinessError } from '@kit.BasicServicesKit';

// 1) 全局：锁定 / 解锁屏幕旋转
async function setGlobalRotationLocked(locked: boolean): Promise<boolean> {
  try {
    await screen.setScreenRotationLocked(locked);
    return true;
  } catch (err) {
    // 非系统应用会在这里拿到 202：Permission verification failed.
    const e = err as BusinessError;
    console.error(`setScreenRotationLocked failed. code=${e.code}, message=${e.message}`);
    return false;
  }
}

// 2) 全局：读取当前是否已锁定（用于回读校验，而不是只看调用是否成功）
async function isGlobalRotationLocked(): Promise<boolean | null> {
  try {
    return await screen.isScreenRotationLocked();
  } catch (err) {
    const e = err as BusinessError;
    console.error(`isScreenRotationLocked failed. code=${e.code}, message=${e.message}`);
    return null;
  }
}

// 3) 全局：设置屏幕方向
//    注意：文档明确说明——设置方向需符合应用旋转策略才会生效，
//    不符合时方向不变且不抛异常，因此必须回读实际方向做校验。
async function setGlobalOrientation(orientation: screen.Orientation): Promise<boolean> {
  try {
    const screens = await screen.getAllScreens();
    if (screens.length === 0) {
      return false;
    }
    await screens[0].setOrientation(orientation);
    return true;
  } catch (err) {
    const e = err as BusinessError;
    console.error(`setOrientation failed. code=${e.code}, message=${e.message}`);
    return false;
  }
}

// 4) 窗口侧的系统接口（旋转锁定）
//    具体签名以 full SDK 中的 d.ts / 系统接口文档为准，此处只示意调用位置。
async function setWindowRotationLocked(win: window.Window, locked: boolean): Promise<boolean> {
  try {
    // @ts-ignore 系统接口，public SDK 无声明
    await win.setRotationLocked(locked);
    return true;
  } catch (err) {
    const e = err as BusinessError;
    console.error(`window.setRotationLocked failed. code=${e.code}, message=${e.message}`);
    return false;
  }
}
```

### 4.3 落地建议

1. **能力探测优先**：任何特权调用前先做「能不能调通」的探测（或统一捕获 202），
   失败即降级，**绝不把失败呈现为「已锁定」**；
2. **回读校验**：调用后必须用 `screen.isScreenRotationLocked()` / 实际方向回读确认，规避「静默不生效」；
3. **幂等**：锁/解锁、设方向都做成幂等操作，重复调用不产生副作用（与安卓版 `RotationController` 的约定一致）；
4. **接口隔离**：特权调用全部收敛到一个后端实现类里（见 5.3），public 构建里换成空实现。

## 5. 推荐产品形态与架构

### 5.1 定位（普通应用身份）

> **屏幕方向控制（鸿蒙版）= 解决「本应用内躺姿乱转」的方向控制工具 + 系统旋转锁定的最省事引导器 + 预留特权后端。

具体拆成四块：

| 模块 | 内容 | 说明 |
|---|---|---|
| ① 应用内方向策略 | 竖/横/跟随传感器/固定方向等策略切换，作用于本应用窗口 | 唯一真正生效的能力，做扎实 |
| ② 系统设置引导 | 一键跳「显示和亮度」（`settings.openDisplaySettingsPage(context)`，API 26，Phone/Tablet/PC 可用），并提供控制中心旋转锁定的图文步骤 | 让用户两次点击完成系统级锁定，**由系统执行，不是我们执行** |
| ③ 可插拔特权后端 | `PrivilegedRotationBackend` 接口，默认实现能力为 `none`；系统签名版替换实现 | 代码结构不阻塞未来定制交付 |
| ④ 外部 Want 指令 | 通过 Want 触发本应用的策略切换 | 对齐安卓版 `am start` 的用法，供自动化/快捷方式调用 |

### 5.2 边界（必须写清楚）

- **不做**「按应用规则」（鸿蒙无合法感知途径）；
- **不做**「全局自动锁定」（三方做不到，写了就是虚假宣传）；
- **不承诺**磁贴/悬浮球与 Android 版等价，除非真机验证通过；
- 躺姿引擎保留，但**只作用于本应用窗口**，UI 上必须写明。

### 5.3 后端接口（工程实际代码 `harmony/LazyRotate/entry/src/main/ets/core/Contract.ets`）

默认构建里只有一个后端：`SelfWindowBackend`——它调用 `window.setPreferredOrientation()`，只作用于本应用主窗口，`canAffectOtherApps = false`。

```ts
// 工程实际接口（节选）
export interface RotationBackend {
  readonly id: string;
  readonly displayName: string;
  /** 是否能影响本应用之外的窗口/应用。public SDK 下恒为 false。 */
  readonly canAffectOtherApps: boolean;
  isAvailable(): boolean;
  apply(target: RotationTarget): Promise<RotationOutcome>;
}
```

系统签名版只替换一个类，UI 与其它入口（悬浮球、外部指令、启动恢复）无需改动：

| 后端实现 | `canAffectOtherApps` | 「锁定」按钮的实际行为 |
|---|---|---|
| `SelfWindowBackend`（默认，public SDK） | `false` | 调用 `window.setPreferredOrientation` 锁定**本应用窗口**，并显示「本应用已锁定 · 系统级锁定请前往设置」的引导条 |
| `SystemRotationBackend`（示例，需系统签名 + full SDK） | `true` | 调用 `screen.setScreenRotationLocked` / `screen.setOrientation` 做全局锁定，并以回读结果确认；失败降级为引导 |

示例类见 `harmony/LazyRotate/docs/SystemRotationBackend.example.ets`（**不在默认构建内**，放在 docs 目录仅作参考）。

### 5.4 外部 Want 指令

```ts
// harmony/ 侧：外部指令入口（示意）
// 通过 Want 携带 action + 参数拉起本应用 UIAbility，在 onNewWant 中解析并切换策略。
// action 与参数名由本应用自定义并冻结，避免与系统 action 冲突。
// 调用方（另一应用 / 自动化工具）示例：
//   let want: Want = {
//     bundleName: 'com.lazyrotate.app',
//     abilityName: 'EntryAbility',
//     action: 'com.lazyrotate.app.action.SET_ROTATION',
//     parameters: { target: 'landscape' }
//   };
```

**要求**：参数解析必须容错（未知 `target` → 忽略并保持现状，不崩溃），
与安卓版「不确定就不动」的原则保持一致。

### 5.5 `harmony/` 工程的实现边界

| 做 | 不做 |
|---|---|
| 本应用窗口方向策略 + 策略切换 | 任何系统接口（`screen.*` 系统接口、`window.setRotationLocked`） |
| 系统设置引导（`settings.openDisplaySettingsPage`） | 全局锁定/全局翻转的「已实现」承诺 |
| 外部 Want 指令 | 无障碍注入（平台已关闭） |
| 躺姿传感器建议（仅作用于本应用窗口） | MDM / root / 刷机相关能力 |
| `RotationBackend` 接口 + `SelfWindowBackend` 默认实现 | 特权后端的真实调用 |
| 特权后端的**示例文件**（`harmony/LazyRotate/docs/SystemRotationBackend.example.ets`，不进默认构建） | 把系统接口编译进默认产物（public SDK 编译不过） |

> 一句话：**默认构建永远是「诚实的三方应用」；特权能力只以接口和示例的形式存在，由定制交付时替换实现。**

## 6. 风险与合规

| 风险 | 说明 | 应对 |
|---|---|---|
| **系统接口滥用** | 调用系统接口会直接得到 202；若包装成「开关」会误导用户 | 默认实现不调用；特权实现只在系统签名构建中出现 |
| **权限申请被拒** | `MANAGE_SETTINGS` 为 `system_basic` + `ACL true`，普通应用申请不到 | 不在 public 版本的 `module.json5` 中声明该系统权限 |
| **商店审核** | 宣称「全局控制其它应用方向」属于虚假/过度承诺；涉及无障碍、悬浮窗、系统设置的能力都是审核敏感项 | 文案只描述已验证能力；不写「全局」二字（除非系统签名版单独分发） |
| **MDM 资质** | 需企业证书 + 激活设备管理应用，且没有旋转策略 | 不纳入路线 |
| **`hdc` 脚本脆弱性** | 依赖 PC、UI 坐标与系统版本，失败即误触 | 仅作为文档兜底，不做自动重试、不做静默执行 |
| **静默不生效** | `Screen.setOrientation` 在不符合应用旋转策略时**不生效也不报错** | 一律**回读校验**，失败即降级并如实提示 |
| **隐私** | 躺姿引擎读传感器；「按应用规则」在鸿蒙不可用，因此**不需要**读取前台应用信息 | 不申请网络权限；传感器数据仅本地计算；不做用户画像 |
| **误导性引导** | 引导用户去系统设置时，不能暗示「我们已锁定」 | 引导前后状态由系统决定，UI 如实显示「系统侧锁定：未知/已开启」 |

**一条更硬的合规红线**：本应用**不得**提供绕过系统权限（root/刷机/漏洞利用）的功能或教程。
若客户确实需要全局能力，正确做法是走**系统签名/预置定制**，把能力放进定制固件，而不是在消费级应用里做越权。

## 9. 一页纸总结

- **能做的**：把本应用自己的窗口方向控制做到极致；一键把用户送到系统「显示和亮度」页面完成系统级锁定；保留躺姿引擎与外部 Want 指令；代码里预留特权后端。
- **不能做的**：全局锁定别的 App、全局翻转 180°、按应用规则、靠无障碍或 MDM 变通。
- **唯一的全局答案**：系统签名 / 预置应用（`screen.setScreenRotationLocked` 等系统接口），代价是 full SDK + 系统签名 + 拿不到普通 AGC 发布。
- **产品底线**：宁可如实告知「本应用只锁自己，系统锁定请点一下这里」，也不做任何做不到的承诺。
